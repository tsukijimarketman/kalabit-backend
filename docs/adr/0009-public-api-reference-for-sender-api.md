# ADR-0009: Publish the Sender API's OpenAPI document and Scalar reference in production

- **Status:** Accepted
- **Date:** 2026-11-13
- **PRD reference:** Docs as code (p.32–33); Build Plan .NET 10 and OpenAPI/Scalar decisions (p.1–2)

## Context

The usual default is to serve Swagger or Scalar only in development, so internal API details are not exposed. But the Sender API *is* the product: integrators need its contract to use it. Public email APIs (Postmark, Resend and others) publish their API reference openly.

The admin Web API is different. It serves only our own dashboard and its operators.

## Decision

- **NotificationSenderApi** serves its **OpenAPI document** and the **Scalar API reference in every environment, including production.**
- **NotificationWebApi** (admin) serves them **only in Development**.
- The OpenAPI document is generated by `Microsoft.AspNetCore.OpenApi` and also committed as `docs/openapi/sender-v1.json`, so contract changes show up in pull request diffs.

## Consequences

**Positive**

- Integrators can read and try the API without asking us for documentation, which is the "send your first email in 5 minutes" experience.
- One source of truth: the reference is generated from the code that runs.
- The committed document turns accidental breaking changes into a visible diff in review.

**Negative**

- Anyone can see every Sender endpoint and schema. Endpoint security has to rely on authentication and authorization, never on hiding routes. Trying a request in Scalar still needs a valid API key.
- Every documented field is a public promise, so descriptions and examples must be kept accurate.

## Revisit when

- Never for the Sender API. Keep the admin API reference off in production.
