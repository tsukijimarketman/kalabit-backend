# What I Learned Today

Today, I learned about implementing **health check endpoints** in a system to monitor its liveness and readiness. Liveness checks help determine whether the application is still running, while readiness checks determine whether it is ready to handle requests. For example, a system should not report itself as ready if it still needs to establish a database connection or initialize essential services. This prevents the application from claiming readiness prematurely.

I also learned the importance of designing **predictable and consistent API routes**. Being a good software developer or software engineer is not about writing code that is overly abstract, clever, or complicated. It is about keeping things simple by following the KISS principle: _Keep It Simple, Stupid._ Code should be readable, maintainable, and predictable so that other developers can understand it without spending unnecessary time investigating how it works.

Another important lesson I learned is to make **return values and responses descriptive rather than generic**. Instead of returning something vague, such as `result`, we should use meaningful names and provide clear response structures that communicate what happened. This makes the code easier to understand, debug, and maintain.

I also learned how to design **RESTful API endpoints** more effectively. Instead of creating separate routes such as `/api/getOrders` and `/api/createOrders`, we can use a resource-oriented route like `/api/orders` and let the HTTP method determine the action:

- `GET /api/orders` — Retrieve a list of orders.
- `GET /api/orders/123` — Retrieve a specific order.
- `POST /api/orders` — Create a new order.
- `PUT /api/orders/123` — Replace an existing order.
- `PATCH /api/orders/123` — Partially update an existing order.
- `DELETE /api/orders/123` — Delete a specific order.

This approach makes the API more consistent because the route identifies the resource, while the HTTP method defines the operation. It also avoids unnecessary repetition in endpoint names.

Finally, I learned the difference between using a **path parameter** and a **query parameter**. When retrieving a specific resource, such as an order with the ID `123`, using `/api/orders/123` is generally more appropriate because the ID identifies a particular resource. Query parameters, such as `/api/orders?status=pending`, are better suited for filtering, searching, sorting, or customizing a collection of resources.

I also learned about **database indexing** and how it can improve query performance when fetching data. Without a suitable index, a database may need to perform a sequential scan, checking records one by one until it finds the matching data. This can become inefficient as the number of records increases.

An index provides a more efficient way to locate data. For example, PostgreSQL commonly uses a **B-tree structure** for indexes. A B-tree organizes values in a way that allows the database to navigate toward the desired value instead of checking every record sequentially. It is similar to looking up a word in a dictionary: rather than reading every word from the beginning, we narrow down the section where the word is likely to be found.

In Entity Framework Core, I learned that I can configure an index using `HasIndex()`. For example:

```
builder.HasIndex(client => client.KeycloakClientId)
    .IsUnique()
    .HasDatabaseName("ux_clients_keycloak_client_id");
```

This creates a unique index on the `KeycloakClientId` property. PostgreSQL can use this index to improve queries that search for a client using its Keycloak client ID. I do not need to explicitly reference the index in my LINQ queries because PostgreSQL's query planner decides whether using the index is beneficial.

I also learned that `HasIndex()` does not automatically make an index unique. The `IsUnique()` configuration adds the rule that duplicate values are not allowed. A normal index can improve lookup performance without preventing duplicates, while a unique index provides both lookup benefits and data integrity enforcement. Indexes also have trade-offs because they consume storage and may add overhead to insert, update, and delete operations.

Another important lesson I learned is the importance of **protecting data at multiple layers of an application**. Rather than relying on a single validation mechanism, we should establish three layers of protection: the frontend layer, the service layer, and the database layer. Each layer has a different responsibility, and together they help maintain data integrity, improve the user experience, and prevent invalid data from being stored.

The **frontend layer** is responsible for input validation and providing immediate feedback to users. For example, if a user enters a negative value for a daily quota, the frontend can display a validation message before the request is submitted. This makes the application easier to use because users can correct mistakes immediately. However, frontend validation alone is not enough because requests can bypass the frontend entirely.

The **service layer** is responsible for enforcing business rules and handling errors in a way that provides a clear and descriptive user experience. For example, if a client with the same Keycloak client ID already exists, the service can detect the conflict and return a meaningful error message instead of exposing a raw database exception. This layer helps ensure that business rules are enforced consistently and that users receive understandable feedback when an operation cannot be completed.

The **database layer** provides the final line of defense through constraints such as unique constraints, check constraints, and foreign key constraints. These protect the integrity of the data even if an application bug, an unexpected request, or another application attempts to insert invalid data. For example, a check constraint can prevent a negative daily quota from being stored, while a unique index can prevent duplicate Keycloak client IDs. These rules are enforced by the database itself, regardless of whether the request passed through the frontend or service layer.

The key lesson is that each layer should have its own responsibility rather than relying entirely on another layer for protection. The frontend improves usability, the service layer enforces business rules and communicates errors clearly, and the database guarantees that essential data integrity rules cannot be violated. This layered approach makes an application more reliable, secure, and maintainable.

Overall, today's lessons reinforced that good software engineering is not about making code look impressive or unnecessarily sophisticated. It is about making systems reliable, APIs consistent, database queries efficient, and data protected at every layer. Writing simple, predictable code and understanding how the underlying systems work allow us to build applications that other developers can understand, maintain, and extend with confidence.

## Technical Takeaways

- **Liveness vs. readiness:** Liveness asks, "Is the application still functioning, or should it be restarted?" Readiness asks, "Can the application handle requests right now?" A database failure might make an application unready without necessarily meaning it should be restarted.
- **Descriptive results:** Prefer meaningful variable names and clear response structures over vague names like `result`. However, a variable named `result` is not inherently bad if its meaning is obvious from context.
- **RESTful routes:** `/api/orders` is a conventional resource-oriented route. The HTTP method determines the operation, but the exact route structure is a design convention rather than an absolute rule.
- **Path vs. query parameters:** Use `/api/orders/123` to identify a specific order and `/api/orders?status=pending` to filter orders. Query parameters can serve other purposes, but path parameters are usually clearer for a resource's primary identifier.
- **Database indexing:** Indexes help the database locate matching records efficiently. PostgreSQL commonly uses B-tree indexes, which navigate through an organized tree structure rather than linearly checking every record.
- **Unique vs. non-unique indexes:** `HasIndex()` configures an index, while `IsUnique()` additionally prevents duplicate values. PostgreSQL automatically determines whether an index is useful for a particular query.
- **Index trade-offs:** Indexes can improve reads but consume storage and add overhead to writes, so they should be created based on actual query patterns and requirements.
- **Frontend validation:** Provides immediate feedback and prevents users from submitting invalid input through the user interface.
- **Service-layer validation:** Enforces business rules and returns meaningful errors that help users understand why an operation failed.
- **Database constraints:** Enforce essential data integrity rules, such as uniqueness, valid value ranges, and relationships between tables, even when application-level validation is bypassed.
- **Defense in depth:** Multiple layers of protection make applications more reliable. Each layer has a distinct purpose, and no single layer should be solely responsible for protecting data.

## Key Takeaway

Good software engineering is about making the correct behavior easy to understand and making the system predictable for both users and developers. Simplicity, consistency, and clarity are strengths, not signs of a lack of sophistication. By designing consistent APIs, using indexes appropriately, and validating data at the frontend, service, and database layers, we can build applications that are efficient, reliable, secure, and maintainable.
